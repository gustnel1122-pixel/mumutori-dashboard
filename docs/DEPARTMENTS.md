# 무무토리 ERP — 부서별 페이지 설계

2026-10-03 사용자 요청: 각 페이지를 담당 부서처럼 운영하고 이후 부서별 개발을 독립적으로 진행한다. 모든 부서는 동일한 원장의 상품·거래 식별자를 공유한다. 화면상의 부서 구분은 업무 구분이며 사용자별 접근 권한 기능은 아니다.

## 페이지와 책임

| 부서 | 주소 / 모듈 | 현재 책임 | 다음 개발 후보 |
|---|---|---|---|
| 운영실 | `index.html` / `overview.js` | 전체 흐름, 부서 이동, 확인할 업무, 최근 변경 | 담당자·기한·마감 일정, 부서별 업무 큐 |
| 재무팀 | `finance.html` / `finance.js` | 매출·매입 집계, 원가 미확정·수금 미연결 확인, 입력된 세금계산서 요약 | 증빙 첨부, 월 마감, 판매 원가 연결 후 손익, 신고용 검토 자료 |
| 자금팀 | `bank.html` / `bank.js` | 계좌 거래, 입출금 분류, CSV, 매출 수금 연결 | 잔액 대사, 지급 예정, 대납·차입·회수 보조원장 |
| 상품팀 | `products.html` / `products.js` | 상품번호·사진·판매 상태·가격·바코드·안전재고 | 옵션·세트 BOM, 채널 SKU 매핑, 가격 이력, 승인 절차 |
| 구매팀 | `purchases.html` / `purchases.js` | 발주·구매처·구매/배송/통관비·배부 원가·입고 연결 | 분할 발주·입고, 외화/환율, 구매대행 자료 가져오기, 지급 연결 |
| 판매팀 | `sales.html` / `sales.js` | 매출·정산 예정·실제 수금·출고 연결 | 주문 가져오기, 채널별 수수료·물류비, 부분 수금, 반품 |
| 물류팀 | `stock.html` / `stock.js` | 실사·입출고·반품·폐기·창고 이동 | 로케이션/로트, 바코드 작업, 할당·예약 재고, 재주문 제안 |
| 협력관리 | `partners.html` / `partners.js` | 거래처명·연락·사업자번호·메모 | 원장의 구매처·판매처를 거래처 ID로 연결, 증빙 파일 |
| 운영관리 | `audit.html`, `settings.html` | 변경 이력, 계좌·창고, CSV/JSON, 백업·병합 | 사용자 권한, 자동 백업, 데이터 보존·복구 정책 |

위의 다음 개발 후보는 기획이며 아직 구현 완료나 자동 실행 약속이 아니다. 업무 우선순위를 사용자가 정하면 해당 부서부터 진행한다.

## 공통 데이터 계약

- 상품의 기준은 `products[].id`. 매입 품목 `lines[].sku`, 매출 `sku`, 입출고 `sku`는 이 값을 참조한다.
- 구매 문서는 `purchaseEvidence[].orderNo`, 판매 문서는 `channelTransactions[].id`.
- 입출고는 `sourceType` + `sourceId` + `sku`로 문서를 참조한다. 원래 문서 수량을 넘는 중복 입출고를 막는다.
- 실제 수금은 `linkedBankIds[]`로 통장 기록 `bankTransactions[].id`에 연결한다. 같은 입금의 중복 수금 연결을 막는다.
- 화면에 같은 데이터를 복제 저장하지 않는다. 다른 부서로 이동할 때 원장과 식별자를 재사용한다.
- 상품 행에서 해당 상품의 구매·재고·판매로 이동한다. 구매 문서에서 연결 입고 원장으로, 물류 원장에서 원래 구매·판매 문서로 이동한다.
- 거래처 원장은 현재 이름 기반의 기존 구매·판매 텍스트와 별개다. 거래처 ID 연결은 향후 스키마 개선 대상이며 현재 연결됐다고 표시하지 않는다.

## 구현 경계

- 10개 실제 HTML 주소. 새로고침·즐겨찾기·뒤로 가기·새 탭 직접 진입 가능.
- `src/departments.js`: 부서 목록, 탐색 구조, 아이콘, 관련 부서.
- `src/pages/*.js`: 해당 부서 렌더러. 페이지 진입 시 해당 모듈 한 개만 동적 로딩한다.
- `src/erp-app.js`: 공통 탐색·검색·페이지 처리와 등록/수정 모달. 여러 페이지의 원장 작성 방식이 서로 달라지지 않도록 공통으로 관리한다.
- `src/erp-core.js`: 분류·검증·원가·재고·집계. 화면 모듈이 직접 별도 계산 규칙을 만들지 않는다.
- `src/store.js`: 저장 어댑터. 기존 localStorage 키를 유지하고 동시 수정 충돌을 검사한다. 다른 탭 저장은 storage 이벤트로 반영하며 열린 초안은 임의 교체하지 않는다.
- `build.py`: 각 페이지 진입점과 콘텐츠 해시 버전을 생성한다. 공통 모듈/현재 페이지 모듈 모두 같은 빌드 버전으로 요청한다.
- 신규 개인 자료를 공개 시드에 추가하지 않는다. `data/seed.json.gz`는 기존 공개 초기 자료만 압축해 보존한다.

## 성능과 저장 확장 단계

1. 이번 구현: 페이지 코드 분리, 현재 페이지 DOM만 생성, 목록 25개씩 표시, 초기 자료 압축/브라우저 캐시, 기존 로컬 저장 호환. 상품 1,200개로 페이지당 25행을 확인했다.
2. 다음 후보: IndexedDB의 상품·거래·입출고·첨부 저장소와 인덱스. 부분 조회·부분 저장, 이미지 분리, 조회용 집계 캐시. 마이그레이션 전 백업, ID·필드 보존과 롤백을 검증한다.
3. 그다음 후보: 인증과 권한이 있는 서버 DB, 동시 사용자 수정 검출, 여러 기기 동기화, 자동 백업. 정적 공개 GitHub를 업무 DB로 사용하지 않는다.

현재 localStorage는 전체 JSON을 읽고 저장한다. 페이지 분리가 저장 용량 제한까지 없애지는 않는다. 은행 자동 연결·여러 기기 동기화·부서별 권한은 미구현이다.

## 디자인 규칙

- 크림색 종이 바탕, 짙은 초록의 주요 조작, 오렌지·블루·라일락·핑크의 부서 포인트.
- 금액은 고정폭 숫자와 색상·문구를 함께 사용하고, 미확정은 0으로 바꾸지 않는다. 강조 정보와 보조 설명의 글자 크기를 구분한다.
- 부서 카드, 포스터·스티커, 작은 캐릭터, 부드러운 페이지 진입·모달·호버·차트 애니메이션.
- 검색 입력마다 페이지 진입 애니메이션을 재생하지 않는다. `prefers-reduced-motion`에서는 움직임을 중단한다.
- 모바일은 부서 선택 메뉴와 반응형 카드, 가로 스크롤 가능한 원장 표, 화면 내부에 맞춘 수정 모달을 사용한다.

## 후속 개발 완료 조건

해당 부서 기능 검증 + 연결 부서에 영향 확인 + 기존 ID/기록 보존 + 모바일 확인 + 실제 배포 확인 + 내부 옵시디언의 현재상태/다음작업/이력 갱신. 업무 수치·개인 정산·문서 ID는 공개 개발 문서에 넣지 않는다.

## 브랜딩 도구 (branding.html)

도장·잉크·포장재를 무엇으로 쓰는지, 고장 나면 같은 판매처·같은 옵션으로 다시 살 정보를 관리한다. 자료는 두 군데로 나뉜다.

| 구분 | 어디에 | 무엇 |
|---|---|---|
| 공개 목록 | `src/branding-data.json` (공개 저장소) | 판매처 상품 사양, 미등록·후보·권고 상태, 표시 가격과 확인일, 판매자 제작 규칙 |
| 내 기록 | 브라우저 장부 `erp.branding` (`mumutori-private-finance-v3`) | 품목 추가·수정, 상태, 발주일·주문번호·주문 내역 주소·수량·실제 결제액·수령일, 도안 원본 위치·제출 버전·좌우 반전, 샘플 시험, 재주문 메모 |

- 내 기록은 다른 장부와 같은 경로를 쓴다: `C.record(data,'branding',row)` 검증 → `store.save` → 변경 이력(칸 이름만, 값은 남기지 않음) → 전체 백업 JSON·백업 병합. 새 서버 저장·인증·보안 규칙은 없다. 칸은 처음 저장할 때 만들어지므로 브랜딩을 쓰지 않는 장부는 그대로다.
- 품목 ID로 겹친다. 공개 목록의 품목에 [기록하기]를 누르면 공개 칸을 채운 수정 창이 열리고, 저장한 뒤로는 내 기록이 화면에 나온다(공개 목록 내용은 카드 안 '공개 목록의 안내 보기'로 접혀 있다). 내 기록을 취소하면 공개 내용으로 돌아가고 복구할 수 있다.
- 상태는 미등록 → 후보 → 권고 → 주문 완료 → 수령 → 사용 중 → 단종·대체. 증거 없이 올리지 않는다: 주문 완료는 발주일, 수령은 수령일, 사용 중은 수령일이나 사용 근거가 있어야 저장된다. 공개 목록은 권고까지만 쓴다.
- 공개 경계는 세 겹이다. ① 공개 목록은 JSON 한 파일이고 비공개 칸 자체가 없다(주문·도안 원본 칸 없음). ② `build.py`가 다른 것을 만들기 전에 `brand_public_check.py`로 그 JSON의 구조를 검사한다 — 허용 목록의 칸·형식·값만 통과하고(칸 이름에 따옴표를 붙이든, 중첩하든, 같은 칸을 두 번 적든 실패), 글 값에 파일 위치(윈도우 드라이브·역슬래시·UNC·POSIX·홈·file:)·허용한 판매처 밖 주소·메일·전화번호·파일 ID 같은 긴 문자열이 있으면 멈춘다. 멈춘 빌드는 화면 파일을 하나도 만들지 않고, 검사 기록에 값 자체는 남기지 않는다. ③ 화면(`src/pages/branding.js`의 `pub()`)은 허용한 칸만 읽으므로 공개 자료에 다른 값이 섞여도 화면·수정 창·저장 자료로 넘어가지 않는다. `tests/branding.test.js`가 python 검사를 실제로 돌리고(없으면 실패) 표식을 넣어 세 가지를 모두 확인한다.
- 공개 목록에 칸이나 판매처를 늘릴 때는 `brand_public_check.py`의 허용 목록(`TOP`·`ITEM`·`INK`·`PRICE`·`ART`, `ALLOWED_HOSTS`)을 먼저 고친다. 자유 글 칸에 사람이 일부러 적는 비공개 내용(예: 글로 풀어 쓴 주문 정보)까지 기계가 막지는 못한다 — 그 부분은 검토로 본다.
- 백업 가져오기·병합으로 들어오는 브랜딩 기록에도 직접 등록과 같은 검증(`validateBranding`)을 적용한다. 증거 없는 주문 완료·수령·사용 중이나 형식이 틀린 기록이 하나라도 있으면 가져오기 전체를 거절하고(어느 기록의 무엇이 문제인지 알림) 현재 장부는 그대로 둔다. 브랜딩 기록이 없는 예전 백업과 정상 기록은 예전 병합 규칙 그대로다. 취소한 기록을 복구할 때도 같은 검증을 거친다.
- 한계: 브라우저 장부라 기기 사이에 자동으로 맞춰지지 않는다(전체 백업을 가져와야 한다). 에이전트가 대신 내 기록을 채울 수 없다 — 에이전트는 공개 목록만 고친다. 기기 간 공유가 필요하면 로그인과 보안 규칙이 있는 별도 저장이 필요하며, 이는 사장님 승인 사항이다.
- 확인하지 못한 값은 공개 목록에서 `null`로 두어 화면에 '확인 전'으로, 내 기록에서 비워 두어 '기록 없음'으로 보이게 한다(지어내지 않는다).
