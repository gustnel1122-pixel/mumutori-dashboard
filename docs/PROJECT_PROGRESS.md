# 운영 홈 프로젝트 그래프

화면은 `index.html#progress`, 자료는 `src/project-progress.json` 한 곳입니다. `src/project-progress.js`가 매번 네트워크로 읽으며 JSON은 서비스 워커에 저장하지 않습니다. 기존 카드의 자료는 `src/project-data.js`에 있으며 같은 프로젝트의 상태가 달라지면 함께 맞춥니다.

## 자료를 갱신하는 AI

1. 최신 내부 정본·지시·완료 회신을 읽고 공개 가능한 업무 요약만 만듭니다. 내부 문서 본문·Drive ID·세션 주소·금액·원가·정산·고객 정보는 넣지 않습니다. 비공개 정산은 세부 상태 없이 내부 확인 자리만 둡니다.
2. `stage`는 통과한 관문 수(0~5), `stages`는 프로젝트 고유의 관문 이름 정확히 5개입니다. 0은 첫 관문 진행 전/미평가, 5는 모든 관문 검증 완료입니다. 공정률·시간 비율이 아닙니다. 승인·설치·시험·배포·실가동은 증거에 따라 구분합니다.
3. `lastActivity`는 실제 결정/작업/검증이 생긴 한국 날짜입니다. 단순 재조회일로 올리지 않습니다. 근거 없으면 null입니다. `checkedAt`/`updatedAt`은 이번 대조 시각입니다. `evidence`는 공개 가능한 근거 명칭만 씁니다.
4. `state`는 active/waiting/paused/unknown/done, `tone`은 green/amber/red입니다. 멈춘 일을 임의 재개하지 않습니다. 7일 이상 움직임이 없거나 진행일 없음·상태 unknown이면 빨간 재확인 표시가 자동 계산됩니다. 점검 자체가 2일 이상 오래되면 화면 위 경고가 뜹니다.
5. 마일스톤의 confirmed(확정 기준), proposed(제안), previous(이전 일정)를 구분합니다. 10/27 18:45 사장님 지시로 오픈 목표는 11/10(화), 11/1은 이전 일정입니다. 목표일이 지나도 실제 오픈 증거 전에는 오픈 완료로 바꾸지 않습니다. `agents`는 담당 역할이며 실시간 접속 표시가 아닙니다.
6. `automation.status`에 예약 연결과 실제 회차 검증을 구분합니다. 실제 회차가 게시까지 성공했을 때만 `lastVerifiedRun`을 갱신합니다. 실패하면 이전 검증 시각을 유지하고 내부 결과에 이유를 적습니다.
7. 최신 main부터 시작해 변경→`python check_project_progress.py`→`python build.py`→`python tests/pwa_build.py`→화면/필터 검수→diff 확인→같은 main에 게시합니다. 새 브랜치·새 사이트는 만들지 않습니다. 기대한 head가 바뀌면 새 main을 읽고 재적용하며 강제 덮어쓰지 않습니다.
8. Pages 성공과 공개 JSON/HTML 일치를 확인하고 내부 순찰 결과에 변경 항목·커밋·게시 확인/실패를 적습니다. 기록 파일 저장이나 GitHub 커밋만으로 화면 갱신 완료라 하지 않습니다. 변경이 없으면 불필요한 커밋을 만들지 않습니다.

재무·고객 DB·보안 규칙·사용자 체크·가격·재고·광고는 이 자료 갱신 범위 밖입니다. 자동화 일정은 내부 순찰 지침을 따릅니다.

## 큰 프로젝트만 관리 — 2026-10-27 20:12 사장님 지시

- 큰 프로젝트는 정확히 11개입니다: offline / letter / mall / smartstore / coupang / product / marketing / finance / brand / support / ops. 새 큰 프로젝트는 사장님 승인 때만 추가하며, 승인 후 검사기의 허용 목록도 함께 변경합니다.
- 새 일은 기존 큰 프로젝트의 `includes`(하위 작업 ID 목록)와 `next`에 넣습니다. `includesLabel`에는 화면 이름 아래 회색 한 줄로 표시할 짧은 포함 항목명을 씁니다. 원래 하위 ID는 승인된 큰 프로젝트 안에 유지하고 다른 묶음에 중복으로 넣지 않습니다. 참고 조사·책·색은 독립 프로젝트로 넣지 않습니다. buttermilk는 프로젝트 목록/포함 목록에서 제외합니다.
- 큰 프로젝트마다 자체 5관문을 정합니다. `stage`는 포함 항목의 숫자 평균·최댓값으로 만들지 않고 그 큰 프로젝트의 관문별 완료 증거로 정합니다. 보조 작업이 멈췄거나 미확인이면 `status`·`next`·`blocked`에 남기고 전체 완료로 부풀리지 않습니다. `lastActivity`는 실제 포함 항목의 최근 움직임을 근거로 하며 단순 합치기·점검으로 날짜를 올리지 않습니다.
- 그래프는 정적인 11개 행입니다. 클릭/키보드로 펼치는 `details`·`summary`·토글·숨은 상세·행 클릭 동작을 추가하지 않습니다. 단계·상태·다음 할 일은 처음부터 보이며 포함 항목은 이름 아래 회색 한 줄만 둡니다.
- 그래프와 기존 프로젝트 카드/허브는 같은 JSON을 `project-feed.js`로 한 번만 읽습니다. `project-data.js`는 이 자료에서 11개 카드를 만듭니다. 옛 `?project=<하위 id>`는 `includes`로 큰 프로젝트를 찾아 주소를 정규화합니다. 과거 characters와 삭제된 책의 북마크는 브랜드 큰 프로젝트로만 이어지며 별도 프로젝트로 복원하지 않습니다. 캐릭터 작업 도구 characters.html 자체는 보존합니다.
- 하루 두 번(02:10·13:10 KST) 자동 갱신도 이 규칙을 지킵니다. 매 회차 `python check_project_progress.py` → `python build.py` → `python tests/pwa_build.py` → PC·휴대폰 화면 확인 → main 게시 → Pages·공개 파일 확인 순서입니다. 검사기는 큰 프로젝트 11개·기존 하위 ID의 소속·중복·제외 항목·날짜·민감 필드를 확인합니다. 검사 실패를 우회해 게시하지 않습니다.
